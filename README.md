# 酒店收入增长诊断系统

`revenue-diagnostic` 是一个面向在营酒店的收益增长服务系统规划，旨在帮助酒店业主和收益管理顾问整理经营数据、评估定价与渠道情景，并形成可追溯的诊断和行动建议。

> **当前状态：需求评审阶段，已有静态交互 Demo。** 本仓库以产品和设计文档为主，尚无连接后台的应用。PRD V0.3.2 为评审草案，不是已批准的开发规格；一期范围、业务规则、技术选型和合规方案均需确认。

## 产品概览

系统拟由**业主端、顾问工作台和服务端诊断引擎**组成。微信小程序是一期候选平台，最终平台仍待确认。

- **酒店业主或经营负责人**：提供并确认经营数据，查看阶段性结果和已交付报告，按授权记录试验结果。
- **收益增长顾问**：管理已授权酒店，审核诊断和报告，交付并人工跟进经营行动。
- **运营及管理员**：在授权范围内管理规则、账号和审计；角色本身不自动授予酒店经营数据访问权。
- **品牌方**：在相应权限要求下接收试价或渠道调整申请；一期不建设品牌方协同工作台。

## 核心业务流程

必要告知和同意 → 首诊分流 → 确认适用性及酒店授权 → 上传或录入资料并逐项确认 → 数据分级与诊断 → 顾问审核 → 报告交付 → 试验及其他行动的人工跟进。

非在营、阶段未知或适用性未确认时，保留资料并等待人工评估，不直接套用在营诊断。阶段性结果不等于已审核交付的正式报告。

## 规划能力与阶段

| 阶段 | 规划内容 |
|---|---|
| P0 一期闭环 | 首诊分流、酒店授权、向导和截图核对、经营指标、竞品与渠道诊断、加佣/投流/促销情景、顾问审核交付及人工跟进。可选记录费用和新媒体事实；新增及细化范围仍待甲方确认 |
| P1 后续 | 收费、权益及支付模式；独立免费预检入口 |
| P2 后续 | 自动提醒、自动归因和完整自动复盘；其他 OTA 专项及全服务型酒店模块 |

上述为规划优先级，不代表功能已经开发、上线或签收。具体范围和验收以 PRD 及后续评审为准。

## 关键业务与数据边界

- **先确认再计算**：识别结果必须由有权主体确认；未知、未确认和不适用不等于零。
- **数据分级**：L1 展示可计算的基础事实和用户自设情景；L2 在同期口径满足要求时分析量价变化；L3 还需可比竞品。具体入级口径、逐日期数据和已发布规则共同决定可输出的结论。
- **区分口径**：周期汇总与逐日事实分别保存；订单、间夜、收入和渠道漏斗不得混用，预算、归因和预测不等同实际增量。
- **不承诺收益**：收入持平不等于利润持平；渠道净收益、部分费用小计不等于酒店 GOP 或净利润。缺少数据或批准规则时，应说明无法判断及缺项。
- **版本与授权**：报告绑定输入及计算快照，修改后须生成新版本并重新审核；线上开放、线下发送、确认接收和阅读分别记录。数据处理、撤权和删除按最终批准的策略执行。

一期不自动抓取平台数据、同步 PMS、修改价格或渠道，也不自动派单、核算酒店利润或替代投资决策。详见 PRD 的范围及上线门槛。

## 评审和开发准备

开发基线冻结前，需确认一期范围、目标酒店及平台、诊断和渠道规则、财务口径、审核与行动权限、数据处理及留存删除策略，并完成相应验收设计。业务规则正式发布还需经授权、脱敏的真实案例验证；合成数据测试不能替代真实业务验收。

## 数据库初始化（评审用）

首版脚本面向 **PostgreSQL 14+**，仅创建 `revenue_diagnostic` schema 及其表、索引和约束，不创建数据库、账号、扩展或业务规则数据。UUID 由应用提供；时间使用 `timestamptz`，未知数值保留 `NULL`。脚本尚未完成业务和合规评审，不应直接用于生产。

在已创建的**空测试数据库**中执行一次：

```powershell
psql -v ON_ERROR_STOP=1 -d revenue_diagnostic_test -f .\src\database\001_initial_schema.sql
psql -v ON_ERROR_STOP=1 -d revenue_diagnostic_test -f .\tests\database\test_initial_schema.sql
```

示例数据库名须替换为实际创建的测试库。连接参数和权限须由执行者按环境配置；若 schema 已存在，脚本会报错并回滚，不会覆盖或迁移已有数据。不得使用真实客户资料进行未获批准的测试。
第二条命令执行合成数据及关键约束测试，测试数据在事务结束时回滚；仅对刚初始化的测试库运行。

物理设计与逻辑字典的主要差异：渠道数据使用 `channel_fact` 按指标逐条记录，保留各自的日期、人群与归因口径；使用 `intake_grant`、`report_delivery_event` 和 `business_job_attempt` 分别保存独立分诊授权、交付事件和任务尝试。快照成员及部分尚待确定的结构以 JSONB 表示。

数据库约束不能替代服务端鉴权、同意检查、字段确认、数据可比性、事实去重、快照不可变、版本冲突、审核交付门禁、删除和备份清理等流程；相关规则、留存及 JSON 结构须评审后实现。表间默认限制删除，清理时须按获批准的范围和依赖顺序处理，不能将审计记录当作恢复已删除资料的来源。
